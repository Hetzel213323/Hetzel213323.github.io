AI + ACCESSIBILITY WORKFLOW

Accessible the first time, tested with people.

AI helps me build and check accessible work faster. It does not replace the people who use it. This page shows the five steps I follow, where a human makes the call at each one, and why testing with real users is still the last word.

A11y-Audit Agent: A11y is shorthand for accessibility: the letter A, the number 11 (for the 11 letters in between), then the letter Y.

Component Comparison

One modal, two versions.

The same modal, built twice. The first version has deliberate accessibility problems and is shown as code only. The second version is fixed and live.

Flawed version

Code only

This version is intentionally flawed and is not rendered as an interactive component on this page. It represents common output when code is written without explicit accessibility requirements.

What I built in on purpose

  • Non-semantic trigger (<div> instead of <button>): Cannot be reached by Tab or activated with Enter or Space (WCAG 2.1.1 Keyboard, 4.1.2 Name, Role, Value).
  • Missing dialog semantics and accessible name: Screen readers do not announce a dialog boundary or title (WCAG 4.1.2 Name, Role, Value).
  • Focus does not move into the modal or stay inside: Keyboard focus remains on the background page while the modal is visually open (WCAG 2.4.3 Focus Order).
  • No Escape key handling: Keyboard users have no standard way to dismiss the overlay (WCAG 2.1.1 Keyboard).
  • Close icon lacks an accessible name: A clickable <span>×</span> provides no label or role for assistive technology (WCAG 4.1.2 Name, Role, Value) and fails minimum target size (WCAG 2.5.8 Target Size Minimum).
  • Focus is not returned to the trigger on close: Closing the modal drops keyboard focus back to the top of the document body (WCAG 2.4.3 Focus Order).

Human-in-the-Loop Process

The five steps I follow.

Each step pairs automated speed with human judgment. AI handles pattern drafting and initial checks, while I make the architectural and usability calls.

  1. Step 1

    Know the platform.

    What AI does

    Summarizes platform documentation and points out likely limits.

    What I decide

    What the platform can and cannot do for accessibility. Every platform has built-in limits. A CMS may lock components so you cannot change their markup or behavior. Unless the documentation says so, you have to build and test to find the limits. Built-in accessibility checkers are a good place to start.

  2. Step 2

    Write to a standard.

    What AI does

    Drafts accessible code to a stated standard (WCAG 2.2 AA) and builds a color contrast matrix for the brand colors.

    What I decide

    Which standard applies, which patterns are appropriate, and whether the code and the contrast results make sense for real content. See the contrast matrix.

  3. Step 3

    Ask a second AI to challenge the first.

    What AI does

    A different AI, or an accessibility-focused reviewer such as WebAIM's AIMee, reviews the code and questions the first AI's assumptions.

    What I decide

    Which flagged issues are real, which are noise, and what to change. Back to the modal demo.

  4. Step 4

    Check what shipped.

    What AI does

    Reviews screenshots of the live page and suggests areas to improve. I also run automated scans.

    What I decide

    What to act on. Screenshots cannot show keyboard order, focus behavior, or what a screen reader announces, so this step has a clear limit.

  5. Step 5

    Test it by hand, and with people.

    What AI does

    Nothing here. This step is manual.

    What I decide

    Everything. I use keyboard-only navigation and the NVDA screen reader, plus axe, WAVE, and Lighthouse. Testing with people with disabilities is the step that cannot be skipped.

Verification Stack

How different tools fit into the workflow.

Automated tools catch different classes of issues depending on whether they inspect rendered DOM rules, raw source code, or design tokens.

Readers and teams may use other tools depending on their stack and testing environment.

Rule-based checkers (axe, WAVE, Lighthouse)

These tools apply fixed rules to a rendered page. Note that Lighthouse's accessibility audit runs on the axe engine, so running both overlaps. They are useful for catching missing attributes or contrast failures, not as independent opinions.

AI review (WebAIM AIMee)

WebAIM's AIMee (opens in new tab) provides an AI review of code, which is useful as a second opinion. It handles a limited amount of code at a time, so it fits individual components better than whole pages.

Code linting while writing (Stark)

Stark (opens in new tab) is described by its maker as accessibility linting that runs in your editor as you or an AI assistant write code. I am aware of it and have not used it yet.

Reusable Component Strategy

Do the full AI-and-review cycle once per component. Save the tested version in a component library. After that, the cycle is only needed for new components or features.

The Last Word

Why real users are required.

Automated checkers and AI reviewers help catch broken markup, missing labels, and contrast math before code ever ships. Still, passing a ruleset is not the same thing as making a product easy for a person to use with assistive technology. On my side, I test with keyboard-only navigation and the NVDA screen reader on desktop. I have not yet done mobile screen reader testing or usability testing with people with disabilities.
